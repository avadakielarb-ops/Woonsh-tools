# АУДИТ КОДА — Woonsh Tools / Multi-Tool Farmer
Дата: 2026-10-23

## Структура репозитория
- **X-File/** — версия коллеги (главный мультитул, ~30+ модулей)
- **X-File-первая-версия/** — первая версия x-file (загрузка на Drive)
- **Фирмы/** — версия пользователя (поиск фирм, ~80+ файлов с тестами)
- **ЦСВ Вайт/** — генератор CSV пользователя
- **Генератор CSV (коллега 3)/** — CSV генератор третьего коллеги
- **woonsh/** — заготовка каркаса (core.py: 169 строк — конфиг, Store, Gemini ротация ключей)

## Задача
Построчная проверка всего кода. Найти лучшее из каждой версии.
Пользователь сказал: его ЦСВ и Фирмы лучше, у коллеги лучше X-File (Drive) и документы.
Нужно найти потоковую загрузку и API-оптимизации из ЦСВ Вайт.

## Папки НЕ ТРОГАТЬ
- Всё что в папке "папка не трогать" (если есть)
- backup_* папки в X-File — только для справки

## 1. ЦСВ ВАЙТ — ppc_gemini.pyw (8129 строк)
**Статус:** ПРОВЕРЕНО ПОЛНОСТЬЮ

### Архитектура API (строки 1196-1410):
- `_request()` (стр. 1230): 5 попыток с экспоненциальным backoff, поддержка Retry-After заголовка, обработка 429/500/502/503/504
- `AUTO_MODEL` цепочка (стр. 1299): `gemini-3.8-flash -> 3.6-flash -> 3.5-flash-lite -> 3.1-flash-lite`
- `_call_model()` (стр. 1350): При RateLimited мгновенно переключается на следующую модель; cooldown по каждой модели в `_auto["cool"]`
- `auto_chain()` (стр. 1312): Валидация цепочки через `list_models()` API
- `_next_daily_reset()` (стр. 1338): Расчёт сброса дневного лимита Google (полночь Pacific = 08:00 UTC)
- Потокобезопасность: `_auto = {"key": "", "chain": None, "cool": {}, "lock": threading.Lock()}`
- `generate_draft()` (стр. 1409): API-режим с multi-turn для ремонта; `responseMimeType: "application/json"` с `responseSchema`

### Потоковые запросы / API оптимизации:
- Streaming-загрузка: **НЕТ настоящего стриминга**. Queue() для UI<->worker, НЕ параллелизм
- Параллельные API-запросы: **НЕТ**. Пакетная обработка ПОСЛЕДОВАТЕЛЬНАЯ (один сайт за другим)
- Пакетная обработка: **ЕСТЬ**: BatchWindow (стр. 6638-8075) — canvas-таблица, _runner() последовательно

### Браузерный режим CDP (строки 1474-2256):
- Собственный WebSocket класс (стр. 1474): Raw TCP, handshake/frames/ping/pong/masking — НОЛЬ зависимостей
- Tab класс (стр. 1561): Выполнение CDP команд, JS через awaitPromise
- keep_awake() (стр. 1583): Защита от browser throttling
- launch_chrome() (стр. 1649): Anti-throttle флаги, отключение Gemini Nano
- browser_generate() (стр. 2017): Новый чат на каждый сайт, retry с перезагрузкой (3 попытки)

### Система валидации (строки 2257-4340) — ЛУЧШАЯ В РЕПОЗИТОРИИ:
- `BANNED_HARD`: ~100+ regex-паттернов для гемблинга на 20+ языках
- `BANNED_CLAIMS_RE`: Непроверяемые утверждения на ~15 языках
- `BANNED_TOPICS`: Все запрещённые категории Google Ads с regex
- `SOFT_BRANDS`: ~60+ названий гемблинг-операторов
- Определение страны: `COUNTRY_ALIASES` (~200 записей), `COUNTRY_HINTS`, `TLD_COUNTRY`, `LANG_TO_COUNTRY`
- `GOOGLE_ADS_LANGS`: Закрытый набор поддерживаемых языков
- `validate()` (стр. 4766): Гео-верификация, проверка языка, English ratio, social casino compliance
- `scrub_description()`: Очистка гемблинг-контента из описаний перед отправкой модели
- Рандомизация структуры кампаний: 4 типа структур, 8 углов, 5 фразировок, 5 акцентов

### Авто-ремонт (строки 4674-4999):
- `AD_SHAPE`/`AD_SCHEMA`: JSON-схема для режима только-объявления
- `repair_snapshot()`: Показывает модели её предыдущий результат с подсчётом символов
- `build_repair_notes()`: Инструкции для ремонта включая детект recidive и truncation
- До AUTO_ROUNDS_MAX раундов ремонта, стоп при stall >= 2 подряд без улучшений

### ПРЕИМУЩЕСТВА (брать в итоговый мультитул):
1. Цепочка моделей с cooldown — мгновенный fallback при лимите
2. CDP WebSocket без зависимостей — чистый TCP
3. Валидация 20+ языков — самая полная проверка гемблинга/запрещёнки
4. Авто-ремонт с recidive detection — умный цикл генерации->валидации->ремонта
5. JSON Schema в API-запросах — структурированный ответ от модели
6. Retry-After заголовок — правильная обработка rate limits
7. Расчёт daily reset — знает когда Google сбросит дневной лимит
8. Рандомизация кампаний — 4x8x5x5 = 800 комбинаций структуры

### ПРОБЛЕМЫ (исправить при слиянии):
1. НЕТ параллельных API-запросов — можно ускорить в 3-5x через ThreadPoolExecutor
2. 8129 строк в одном файле — нужно разбить на модули
3. Захардкоженные модели — нужно в конфиг
4. Нет кэширования результатов
5. 120мс polling — можно заменить на event-driven
6. Нет логирования — print() вместо logging
7. Нет обработки network disconnect
8. Дублирование кода _draft_worker и _many_worker

## ПОТОКОВЫЕ / ASYNC ОПТИМИЗАЦИИ

### Текущее состояние:
1. ЦСВ Вайт — batch СТРОГО ПОСЛЕДОВАТЕЛЬНЫЙ, queue.Queue() только для UI<->worker
2. X-File ads — ЕСТЬ ThreadPoolExecutor (4 workers для pages, 4 для campaigns), но не для batch
3. Генератор CSV (коллега 3) — последовательный + time.sleep(4) блокирует UI
4. X-File company_search — threading + queue, но каждый поиск последовательный

### Что добавить при слиянии:
1. concurrent.futures.ThreadPoolExecutor для batch API (3-5 параллельных запросов)
2. asyncio + aiohttp как альтернатива
3. API worker pool + UI poll loop (queue.get с timeout вместо 120мс polling)
4. Кэширование результатов API
5. Batch API Gemini (когда появится)

### Ускорение:
- Сейчас: 1 сайт ~10с -> 100 сайтов = ~17 минут
- С 3 workers: ~6 минут (3x)
- С 5 workers: ~4 минуты (4x, rate limit)
